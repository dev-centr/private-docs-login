An organization administrator installs the published GitHub App so members of that organization can sign in to private documentation.
Someone who hosts the issuer uses the later sections, on a checkout of this repository or on a host they operate.
Those are different jobs.

A login provider for OpenID Connect-enabled private sites.
It lets GitHub and GitLab organization members sign in to private resources when their organization has installed the app.
It brokers GitHub and GitLab membership for private documentation sites.
The app an owner approves is named Private Docs Login.
GitLab groups opt in by inviting one configured user.
The listen address and the public issuer URL come from config, and only the person hosting the issuer sets them.

== What this is for

The sign-in mechanism is general OpenID Connect: a documentation site sends the reader to this issuer, and the token names the organizations or groups that opted in.
This distribution is for teams who publish private documentation (member-gated docs hubs, handbooks, and internal guides) and want to gate it on GitHub or GitLab organization membership.
It ships as its own product, with one install story, one GitHub App, and setup written for documentation sites, because that job is narrower than a generic identity provider.
The documentation language stays for that reason.
An Antora site behind Cloudflare Access, or another OpenID Connect client, is one common setup, not the only one, and this issuer does not gate arbitrary web applications.

== Install the published app

An organization owner installs the published GitHub App on the organization.
The app is named Private Docs Login.
That installation is how the organization opts in.
GitHub Marketplace is the public catalog for that app when GitHub lists it.
The same opt-in is the organization's install of the app.
You do not clone this repository, and you do not run `private-docs-login`, to install it.

The app asks for two read permissions: Organization members, and the user's Email addresses.
Members read tells the issuer which organizations installed the app.
Email addresses read lets the issuer send the reader's verified primary address, because Cloudflare Access names readers by email.
An organization that has not installed the app is not in the token.
A reader without a verified primary address is refused with a page that says where to verify it.

GitHub's install screen shows the app name, the owner, the permissions, and a short description.
It does not show this repository.
After install, GitHub opens the issuer's setup page.
That page says the installation lets this issuer name the organization's members in tokens for private documentation sites registered with the issuer, that each site still checks for its own organization, and that membership checks pass through the publisher's host.
It also says an Antora site behind Cloudflare Access, or another OpenID Connect client, is one common setup.

A reader stays on this issuer until they continue.
That page states the same limit.
If they do not want sign-in to pass through the publisher, it tells them to stop and give the message, plus this article, to their organization administrator.

A GitLab group owner invites the user the issuer is configured to recognize.
The example name is `private-docs-login`.
Guest access is enough.
A group that has not invited that user is not named in the token.
GitLab does not install apps onto other groups.
Zero opted-in groups is a refusal page, not a token.

== Point the documentation site at the issuer

The person who runs the documentation site registers that site with the issuer.
The site is a client: it has an id, a secret, and exact redirect URLs.
The issuer URLs and the groups claim are in <<relying-parties>>.

Antora does not have a playbook extension for this login.
An Antora site is static.
The usual client in front of it is Cloudflare Access.
The hostname and Allow policy steps are in https://docs.devcentr.org/general-knowledge/how-to/cloudflare-access-static-site/[Cloudflare Access for static sites].
A public Antora site can add a link to the private or team site with https://docs.antora-supplemental.org/related-docs/[Related Docs] (`@antora-supplemental/related-docs`).
That extension puts the link on each page of the public site.
The link opens the private or team site.
facto-stack includes Related Docs.
Readers still sign in through this issuer.

== How login works

The login works like this:

. The private documentation site sends the reader to the issuer.
. The issuer sends the reader to GitHub, using the one published app.
. GitHub comes back to the issuer only.
. The issuer checks that the organization has installed the app and that this person is a member, then sends the reader back to the site.
. The site admits the reader only if the token names that organization.

One published app can gate many organizations' private documentation sites.
Each site asks for its own organization.
Members of one organization are not admitted to another organization's documentation.

The GitHub App has one callback, on the issuer.
Customer documentation URLs are not entered in the GitHub App settings.

A private documentation site is a client of the issuer.
The redirect URI is registered with the issuer.
That list is not the GitHub App.

An outside organization installs the published app.
That organization does not register a new GitHub App, and does not fork this repository, to use the hosted issuer.

== Run your own issuer

An organization administrator may need to run their own issuer when the organization's policies require sign-in to stay on the organization's own host.
The reasons are trust, privacy, residency, the organization's own domain, GitHub Enterprise Server, or claims the published issuer does not issue.

A Marketplace install of the published app cannot be pointed at an issuer the organization hosts.
GitHub only calls the callback URL registered on that app, which is the publisher's host.
Hosting an issuer means registering a separate GitHub App for that issuer.

The usual arrangement is: the publisher runs the issuer, the organization installs the app, and the organization registers its documentation site as a client.

You do not need your own issuer when you trust the publisher's issuer, and organization membership on your own documentation site is enough.
If the publisher's issuer is down, every private documentation site that depends on it cannot sign readers in.

== Host the issuer

These commands run in a checkout of this repository, on a machine you operate, after you have decided to host the issuer.
The command name is `private-docs-login`.
That is the package bin, and the file is `bin/private-docs-login.mjs`.
From the checkout, `npm link` puts `private-docs-login` on your PATH.

Copy `config/issuer.example.sdl` to `config/issuer.sdl`.
The issuer signs each login token with a private key that stays on this machine.
You create that key file.
`PRIVATE_DOCS_LOGIN_SIGNING_KEY_PATH` is the path to the file.
The file format is a PKCS#8 PEM.
Other names are in xref:environment-variables.adoc[Environment variables].

[source,shell]
----
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out signing.pem
private-docs-login serve --config config/issuer.sdl
----

This window shows the process.
The listen line is the address.
Ctrl+C stops it.

Sign-in state (pending requests, one-time codes, and access tokens) is kept in a SQLite file when `PRIVATE_DOCS_LOGIN_STATE_PATH` names one.
A restart then keeps sign-ins that are in progress.
Without it, state is in memory, and the start-up output says so.
SQLite needs Node 22.13 or later.
Run one process per state file.
`/healthz` answers `200` when the signing key and the state store work, and `503` when they do not.

DevCentr's own issuer runs on Cloudflare Workers with D1 instead.
That runbook is xref:deploy-cloudflare.adoc[Deploy on Cloudflare Workers].

== GitHub App for an issuer you host

This section is for the person hosting the issuer.
An organization that uses the published app installs that app.
That organization does not run this command.

[source,shell]
----
private-docs-login github-manifest --config config/issuer.sdl
----

The command prints the owner, the GitHub form URL, and the callback and setup URLs, and refuses to start when `github.owner` is missing or the issuer is not `https`.
Open `http://127.0.0.1:8765/`.
The form posts the manifest to `https://github.com/organizations/<owner>/settings/apps/new`, where `<owner>` is `github.owner` in the config.
The example config and the DevCentr deploy config name `dev-centr`.
The name on that screen is Private Docs Login.
Approve it there.
Credentials land in gitignored `var/`.
The command does not print the client secret or the private key.

The app asks for two read permissions: Organization members, and the user's Email addresses.
Members read tells the issuer which organizations installed the app.
Email addresses read lets the issuer send the reader's verified primary address, because Cloudflare Access names readers by email.
An organization that has not installed the app is not in the token.
A reader without a verified primary address is refused with a page that says where to verify it.

== GitLab application for an issuer you host

This section is for the person hosting the issuer.
A group that only wants to opt in invites the configured user.
That group does not create this application.

[source,shell]
----
private-docs-login gitlab-setup --config config/issuer.sdl
----

GitLab has no GitHub App installation.
The application is group-owned, named Private Docs Login, scope `read_api`.
The instance URL is the `gitlab.instance.url` value.
The example and DevCentr owner group is `dev-centr`.
On gitlab.com the group `dev-centr` is not there yet.
After it exists, the settings page is `https://gitlab.com/groups/dev-centr/-/settings/applications`.
The issuer reads the account's confirmed primary email from `/api/v4/user` with the same `read_api` scope.
Redirect URI is `{issuer}/gitlab/callback`.

[[relying-parties]]
== Relying parties

A `client` block is a documentation site registered with the issuer: id, `secret-env`, and exact `redirect` values.
Cloudflare Access is the example client `cloudflare-access`, generic OpenID Connect.
An Antora site behind Cloudflare Access, or another OpenID Connect client, is one common setup.

* Auth URL `{issuer}/authorize`
* Token URL `{issuer}/token`
* Certificate URL `{issuer}/jwks`
* Scope `openid` (`email` and `profile` are accepted too)
* Client authentication at the token URL: `client_secret_basic` (HTTP Basic) or `client_secret_post` (form fields), one per request

For Basic, the client id and secret are each form-urlencoded, joined with `:`, and base64-encoded, as RFC 6749 section 2.3.1 says.
A request that sends a Basic header and a `client_secret` field is refused with `invalid_request`, and so is a body `client_id` that differs from the Basic one.
A failed Basic attempt answers `401 invalid_client` with a `WWW-Authenticate: Basic` challenge.

The ID token and `/userinfo` carry `email` and `email_verified` (always `true`), from the verified primary address on GitHub or the confirmed primary address on GitLab.
No other address on the account is sent.
The groups claim uses `groups-claim` (default `groups`).
Values look like `github:github.com:example-org` and `gitlab:gitlab.com:example-group`.
The `forge` claim is `github` or `gitlab`.
Client id `generic-rp` is the same shape for another private documentation site.
Adding a client does not replace an identity provider that is already in use.
This issuer does not gate an arbitrary web application.

Another runtime can sit in front of this protocol later.
This repository does not ship that adapter.

[[pages]]
== Pages the issuer serves

Readers see a few HTML pages: the acceptance page before GitHub or GitLab, the forge chooser, the page GitHub opens after an install (`/github/setup`), and the pages that explain why a sign-in stopped.
They share one layout and one stylesheet, follow the system light or dark setting, and say what happened and what to do next.

* The stylesheet, the Space Grotesk font (SIL Open Font License 1.1, Latin subset, about 22 KB), and the logo are served by the issuer itself under `/assets/`, with content-hashed names. No font or stylesheet loads from another host.
* Every page carries a Content-Security-Policy with no inline script or style. `form-action` lists this issuer and the configured GitHub and GitLab origins, because the acceptance form is redirected there.
* The setup page shows the installation id GitHub sends, only when it is a number, and the Cloudflare Access values for this issuer. It shows no client id or secret.
* `npm run preview` starts a local preview with a stand-in forge, so every page can be opened without a GitHub App. The pages are listed at the top of `scripts/preview.mjs`.
* After changing anything in `assets/`, run `npm run assets` to rebuild `src/assets.generated.mjs`. The tests fail when it is out of date.
